## 2026-10-23 修复：两条不同配方不能各占一台台子（实机 `V-B0-5`，原料认领"整堆"→"按量"）

- 现象（用户实机）：两条**不同**配方（广域射线炮 / 电荷步枪）都能在精密装配台上做，全图 2 台；两单都排上后其中一条报红字「这批材料正被另一条产线占用（等它先做完，或给它多备一堆）」（Keyed `DS_BA_Block_Claimed`），两张台子只有一张在跑。用户原话：`无法放多个相同配方,也算符合预期` / `但是这两个都是精密装配台可做，有两个装配台，预期是可以各自找一个台子的`。
- 根因：`Source\AI\CraftIngredientClaims.cs` 的认领表是 `Dictionary<Thing, object>` —— **整堆互斥**。`BillProbe.ExtractIngredients` 对原版 `job.targetQueueB` 的每一堆 `TryClaim(t, owner)`，**任一堆**已被别的线占了就整轮作废 ⇒ 第二条线永远排不上。而两条线共用同一个假 worker pawn（`CompBillAutomation.Worker`）、不真预约，原版选料器不会替我们区分，**两条线必然挑到同一堆料**（`WorkGiver_DoBill.cs:461` 的 `baseValidator` 只查 `pawn.CanReserve`）。
- 修法：
  - `CraftIngredientClaims` 改成 `Dictionary<Thing, List<Claim{Owner, Amount}>>`：只要求 `Σ Amount ≤ stackCount`；新增 `FreeAmountOf` / `ClaimedTotal` / `HasOtherOwner` / `TryClaim(t, owner, amount)`；`Release` / `Sweep` 同步改（`Sweep` 还会把认领按顺序夹回当前堆数，防"账上欠 60、实际 20"）。
  - `BillProbe.ExtractIngredients` 重写成三步：① 照抄原版的 (def, 件数, 挑中的那堆)；② 用 `HaulSourceContents.CollectDirect(map, pool)` 建本图核心的 `def → 堆列表`（大堆优先）；③ 原版那堆优先，余量不够就从同 def 的其它堆补齐（**可跨多堆拆分**）。补不齐才失败，并把"被别人按量占了"与"真缺料"分开报（`HasOtherOwner`）。
  - `RecipeExpansion.Collect` 同步改成按 `FreeAmountOf` 取 `take`；`FillAvail` 的可用量也改用 `FreeAmountOf`（否则展开会按"总库存够"白跑一轮，Collect 才发现不够）。
- 为什么可以跨堆拆：结算侧 `Source\AI\BillCraftFunnel.cs:68-79` 本来就照抄原版 —— `need >= t.stackCount` 整堆拿，否则 `t.SplitOff(need)`，"一堆只拿一部分"是既有能力。
- 校验：Release 0 error（4 条既有 warning）；csproj 131 = 磁盘 131；DLL `Patch_*` 87；`FreeAmountOf` / `ClaimedTotal` / `HasOtherOwner` / `CraftIngredientClaims` 均在 DLL；`Assemblies\DigitalStorage.dll` **430,080 B**，SHA-256 `7128BCF9E7E09DBAE51EF23E8C9543AA5CF112AD93DD9F079F9373F04BB2CF53`；部署 复制 2 / 已一致 49 / 缺失 0（仓库与游戏目录哈希一致）。
- 教训：**"认领"要按量而不是按堆** —— 任何"按对象互斥"的占用表，遇到"多消费者共享一份可拆分资源"都会把并行压成串行，而且报错文案会把真实原因说成"材料被别人占着"，把人往错方向带。

## 2026-10-23 新增工具：`V-B0-4` 一键场景 —— 生成「有头衔 + 有文化」的殖民者

来源：用户需求 —— `V-B0-4写一个dev tool，生成有头衔的文化存在戒律的殖民者`。
验收条目 `V-B0-4`（=[Docs\实机验收-2026-10-17-B0到B2.md](Docs/实机验收-2026-10-17-B0到B2.md) 第 81 行）：
「有头衔的小人 + 与头衔冲突的食物只在核心 ⇒ 该食物**不被抽取**（`WillEat` 判据生效）；换成合规食物则正常」。

### 为什么"手工搭场景"会测出假绿
`RimWorld\FoodUtility.cs:159-179` 的 `InappropriateForTitle(ThingDef food, Pawn p, bool allowIfStarving)` 要生效，必须**同时**满足：

1. `p.royalty != null` 且 `MostSeniorTitle != null`；
2. `royalTitle.conceited == true` —— 而玩家派系的头衔**不会**自动傲慢：
   `RoyalTitleUtility.ShouldBecomeConceitedOnNewTitle`（`RimWorld\RoyalTitleUtility.cs:437-449`）在
   `p.Faction.IsPlayer && !p.IsQuestLodger()` 时返回 `GetConceitedTraits(p).Any()`，
   即小人必须有 `Abrasive` / `Greedy` / `Jealous` 之一（`IsPawnConceited`，`:369-389`；`Ascetic` 一票否决）。
   **没有傲慢特质 ⇒ 头衔的食物要求静默失效，测试假绿。**
3. `royalTitle.def.foodRequirement.Defined`（= `minQuality != Undefined`）—— 低级头衔（Freeholder / Yeoman / Acolyte）**没有**这条；
   带要求的最低帝国头衔是 **Knight**（`XML\Royalty\Defs\RoyalTitles\RoyalTitles_Empire.xml:181`，`<minQuality>MealSimple</minQuality>`，
   `allowedTypes` = `Processed, Liquor`，`allowedDefs` = Ambrosia / Milk / RawBerries）。
4. **不能饿到 `Starving`** —— `InappropriateForTitle(..., allowIfStarving: true)` 在 `p.needs.food.Starving` 时直接返回 false（放行）。
   `Need_Food.CurCategory`（`RimWorld\Need_Food.cs:29-47`）里 `Starving` 仅 `CurLevelPercentage <= 0`。

### 落地：`Source\Components\TitleFoodDevTool.cs`（3 个调试动作，分类 `DigitalStorage`）
- **`V-B0-4-1 生成「有头衔」殖民者 + 冲突食物只放核心（点格子）`**（`DebugActionType.ToolMap`）：

### 修复：并行上限「调小」后手不减（那个上限过去只管加、不管收）

### 严重 bug：堆叠 mod 把 stackLimit 抬到千万级 ⇒ 核心容量判定 int 溢出（已修复）


来源：用户当天报障（两张截图 + Player.log）：**地面上的白银/零部件死活不进核心**；右键菜单只给

**取证（Dev 动作「为何没被自动收纳（点格子）」的 dump 是决定性证据）**：

```

核心「数字存储核心」 在目的地表里=True ... HaulDestinationEnabled=True 优先级=Preferred
```

**反解**：核心 `maxStacks=3000`、`Count=13` ⇒ 剩余堆位 `k=2987`；原版容量 =
`int((3000-13) * stackLimit)`，观测 `-1326444032`，即 `2^32-1326444032 = 2,968,523,264`。
解 `2987 * L ≡ 2,968,523,264 (mod 2^32)` 得 **L = 24,000,000**
（2987 × 24,000,000 = 71,688,000,000 → mod 2^32 = 2,968,523,264 → int32 = -1,326,444,032，与 dump 逐位吻合）。

**24,000,000 从哪来**（玩家整合包两条叠加，全部逐行读源码确认）：

1. Steam `simple.tech`：`1.6\Patches\Increased Stack.xml` 的 `PatchOperationReplace` 把

   （静态 `_baseCounts` 缓存第一次读到的值，此处即 30000），再按模式改写：
   `Scalar` ⇒ `num = max(1, floor(base * Value)); def.stackLimit = num;`
   玩家配置 `Mod_1447140290_OgreStackMod.xml` 里 `SmallVolumeResource_Mode=Scalar`、
   `SmallVolumeResource_Value=800`，而 `OgreStack.Support.RimWorld` 判
   `SmallVolumeResource = FirstThingCategory == "ResourcesRaw" && d.smallVolume` —— 白银正中该桶
   ⇒ **30000 × 800 = 24,000,000**。零部件走 `Manufactured`（`Manufactured_Value=5000`）⇒ 750 × 5000 =
   **3,750,000**（2987 × 3,750,000 = 11,201,250,000 → int32 = -1,683,652,888，同样为负 ⇒ 同样 `Accepts=false`）。

**为什么别人没撞上**：原版货架类 `Building_Storage.maxStacks` 只有个位数（3 之类），

### Bug 修复：制作代理「莫名奇妙不识别，隔一会又好了」（原版选料负缓存粘在我们的 bill 上）

用户报障原话：「制作代理有个bug，会莫名奇妙不识别，隔一会又好了」。定位过程与结论：

- **反馈环**：`Player.log` / `Player-prev.log` 全量搜 `DigitalStorage`/数字存储/制作代理 **0 命中**（`DS_EnableDebugLog` 没开），
  也没有本 mod 的异常 —— 说明不是异常路径，是**状态卡住**；那两条会 `Log.ErrorOnce` 的 5 秒退避（`CompBillAutomation.cs:583/:658`）也被排除。
- **根因（代码级确证）**：代理把「自己造的 bill」长期换进台子选料，而原版
  `RimWorld\WorkGiver_DoBill.cs:263-266` 在**每次选料失败**后写
  `bill.nextTickToSearchForIngredients = now + ReCheckFailedBillTicksRange.RandomInRange`（`:95`，**500~600 tick**），
  `:194` 的硬闸又会在 `TicksGame <= bill.nextTickToSearchForIngredients && FloatMenuMakerMap.makingFor != pawn`
  时**整条跳过这张 bill**（我们借台子时 `makingFor` 恒为 null ⇒ 永远命中）。
  关键点：我们这条 bill **不是临时的**（`CompBillAutomation.MakeLine:419-426` 创建后随 `CraftLine` 活到 `ClearAll`），
  所以原版的负缓存**粘在它身上**：任何一次取活失败（刚做完一件还没补料 / 另一条线占着这堆 / 料被顺走几件）之后，
  代理对本线失明 8~10 秒（1×），且退避期间面板照旧报「缺料（核心里的材料不足）」或干脆「等待中」——
  与「不识别、隔一会又好了」完全吻合。顺带修一个同源隐患：同一次取活里会依次问多个 `WorkGiver_DoBill` 派生类，
  前一个失败写的缓存会让**后一个 giver 直接拿到 null**。
- **改动**（`Source/AI/BillProbe.cs`）：新增 `ResetVanillaNegativeCache(Bill)`，在**每次** `doBill.JobOnThing(...)` 之前把
  `bill.nextTickToSearchForIngredients` 归零；`Diagnose` 判定 `DS_BA_Block_Material`（真没料）时退避改 `CraftBackoffTicks`
  （120 tick / 2 秒）而不是 30，因为清掉负缓存等于把「原版全图候选遍历」的天然限频也清掉了（`WorkGiver_DoBill.cs:525-551`，
  `ingredientSearchRadius` 默认 999 ⇒ 整张图），必须自己限频。`BillProbe.cs:33-35` 那句「我们的 bill 是临时的，写它也没意义」的旧注释是**错误前提**，已改写。
- **效果**：材料恢复后 ≤2 秒重新开工（原来最多 8~10 秒），且失败原因不再被负缓存污染（诊断可信）。
- **校验**：Release 0 error（仅 `AssemblyInfo.cs(16,31)` CS0618 旧警告）；csproj↔磁盘 106=106；DLL `Patch_*` 75；
  DLL SHA-256 `9070A7F847CBB9A6D2A029D2050ED2DEA629554DDB0D5151A1F2A52E1B68BE05`；`Tools\deploy.ps1` 已同步游戏目录（哈希一致）。
- **埋点**：`BillProbe` 外面包了一层 `TryAcquire` 壳，只在 `enableDebugLog` 打开时按「原因变化 / 300 tick」节流打印
  「制作代理取活 成功/失败：原因｜配方｜台子｜清掉了原版负缓存（还剩 N tick）」—— 报障时这一段就是第一现场证据。
- **待实机验证**：让核心短暂缺料（做一件消耗光）→ 补料 → 代理应在 ≤2 秒内开工；若仍复现，下一步开 `DS_EnableDebugLog`
  抓「取活失败原因」逐轮序列（见验收清单新增条目）。
