### 修复：核心能收有毒垃圾 +「清空废料容器」直接把废料送进核心

来源：用户反馈（2026-10-18）：「该 mod 中的存储核心无法存储有毒垃圾，导致『失能机关』的机械组装平台

需要手动禁止有害垃圾存在存储核心中，再自己手动分配一个垃圾存储区。」

**根因（两件事叠在一起）**

1. **原版清空链只认格子**：`WorkGiver_EmptyWasteContainer.JobOnThing:51-58` 把
   `StoreUtility.TryFindBestBetterStorageFor(...)` 的输出 `foundCell` 直接塞进 `targetC`。
   目的地是**容器**时它是 `IntVec3.Invalid`，而 `JobDriver_EmptyThingContainer.TryMakePreToilReservations`
   会去预订这个非法格子 ⇒ 必然失败、**没有任何日志**（玩家只看到"小人永远不来清理"）。
   那条 driver 的收尾是 `CarryHauledThingToCell` + `PlaceHauledThingInCell`，天生只会"放到格子上"。
2. **同一天上午的「默认不收有害垃圾」**（`5764832`）只是把核心从候选里摘出去、让原版退回格子腿：
   问题没修，只是把"核心存不了垃圾"换成了另一条抱怨 —— 所以下午按用户要求反转。

  之后生物塑型舱找料会拿到跨图候选（它那条链没有背包那一跳，小人会走向同名坐标）；
  嵌套调用时 Postfix 直接置 false 会清掉外层的 true。

  本地 `git pull --rebase origin main` 把 8 个未推送提交 rebase 到新 head。

### 核心并发使用：多交互格 + 预约不再独占（已落地）

来源：用户 2026-10-18「核心还是一次只能和小人交互，效率很低。有办法解决吗，例如增多交互格子？」

**先把两条机制分开看**

1. **送货不经过交互格**。原版入库是
   `Toils_Haul.CarryHauledThingToContainer`（`Verse.AI/Toils_Haul.cs:388-407`）→
   `pather.StartPath(targetB.Thing, PathEndMode.Touch)`：贴着 3×3 的**任意一格**都能放下，
   单交互格从来不是送货瓶颈（这也是上一版
   `Patch_HaulToContainer_ConcurrentCore.cs` 注释里写的结论）。
2. **真正挡人的是预约名额**。`ReservationManager.CanReserve`（`Verse.AI/ReservationManager.cs:157-236`）：
   ```csharp
   int num  = target.HasThing ? target.Thing.stackCount : 1;   // 建筑 = 1
   int num2 = (stackCount == -1) ? num : stackCount;
   ...
   if (num3 >= maxPawns || num2 + num4 > num) return false;    // ← 第二个预约者必挂
   ```
   建筑 `stackCount` 恒为 1 ⇒ 无论调用方传多大的 `maxPawns`，第二个人都订不到。
   核心是 3×3 大容器，却和「往工作台塞一份材料」共用同一条规则 ⇒
   同一时刻只有一个人能"占住"它，其余人开局就停在「目标已被预订」。

### 与 Pick Up And Haul 改为**真兼容**（旧立场「声明互斥」作废，已落地）

来源：用户 2026-10-18「来兼容一下 pick up and haul 吧，先去研究对方代码」。
2026-10-12 曾拍板「声明不兼容、不做兼容」，理由是「入库是瞬移，与批量拾取差一个搬运作业」。
读完对方 1.6 源码（工坊 `1279012058`，反编译落在 `_SourceCode\Pick Up And Haul\1.6\Source`）后，
那条理由**站不住**：两者可以共存。

**三条研究结论**

1. **PUAH 看不见核心里的东西。** 它的候选只来自
   `WorkGiver_HaulToInventory.PotentialWorkThingsGlobal`（`listerHaulables`），且每件都要过
   `OkThingToHaul` 的 `t.Spawned`（`WorkGiver_HaulToInventory.cs:143`）。本 mod 的
   `Building_StorageCore` 虽是 `IHaulSource`（内容物会进那张表），但内容物 `Spawned == false`
   ⇒ PUAH 一件都拿不到，不存在"两边抢同一件"。
2. **它不会搬坏核心。** PUAH 自己的目的地搜索（`WorkGiver_HaulToInventory.cs:531-572`）只读
   `AllHaulDestinationsListInPriorityOrder` + `Accepts` + `GetStoreSettings().Priority`，
   跳过 `ISlotGroupParent` 与 `Building_Grave`；真正的入库动作仍是
   `Toils_Haul.DepositHauledThingInContainer` → `ThingOwner.TryTransferToContainer`
   （`Verse\ThingOwner.cs:738-755`，先 `CanAcceptAnyOf` 再 `SplitOff` + `TryAdd`）
   ⇒ 落到本 mod 的 `CoreStorageContainer.TryAdd`，筛选/断电/入库开关三道规则照样生效。
   `Verse\ThingOwnerUtility.cs:34-60` 的 `TryGetInnerInteractableThingOwner` 认
   `IThingHolder` 的 `GetDirectlyHeldThings()`，核心第 32 行实现它、`:120` 返回 `innerContainer`。
3. **唯一的真实摩擦是"瞬移抢在作业之前"。** `ReservationManager.IsReserved` 只认已建立的预订，
   而 PUAH 的组批作业在 `JobDriver_HaulToInventory.TryMakePreToilReservations` 里一次性预订整条
   `targetQueueA` —— 预订前那一瞬、以及预订失败的尾部条目，仍可能被我们瞬移走，让那趟活白跑。
   **对策**：PUAH 在场时强制打开 `Reject.JobTarget` 闸门（不改对方代码）。

来源：用户当天报障（两张截图 + Player.log）：**地面上的白银/零部件死活不进核心**；右键菜单只给


表里有核心、通电、开关全开、筛选允许 —— 只有 `Accepts` 是 false，而且 `还能装` 是**负数**。

**反解**：核心 `maxStacks=3000`、`Count=13` ⇒ 剩余堆位 `k=2987`；原版容量 =
`int((3000-13) * stackLimit)`，观测 `-1326444032`，即 `2^32-1326444032 = 2,968,523,264`。
解 `2987 * L ≡ 2,968,523,264 (mod 2^32)` 得 **L = 24,000,000**
（2987 × 24,000,000 = 71,688,000,000 → mod 2^32 = 2,968,523,264 → int32 = -1,326,444,032，与 dump 逐位吻合）。

**24,000,000 从哪来**（玩家整合包两条叠加，全部逐行读源码确认）：

   `Scalar` ⇒ `num = max(1, floor(base * Value)); def.stackLimit = num;`
   玩家配置 `Mod_1447140290_OgreStackMod.xml` 里 `SmallVolumeResource_Mode=Scalar`、
   `SmallVolumeResource_Value=800`，而 `OgreStack.Support.RimWorld` 判
   `SmallVolumeResource = FirstThingCategory == "ResourcesRaw" && d.smallVolume` —— 白银正中该桶
   ⇒ **30000 × 800 = 24,000,000**。零部件走 `Manufactured`（`Manufactured_Value=5000`）⇒ 750 × 5000 =
   **3,750,000**（2987 × 3,750,000 = 11,201,250,000 → int32 = -1,683,652,888，同样为负 ⇒ 同样 `Accepts=false`）。

**为什么别人没撞上**：原版货架类 `Building_Storage.maxStacks` 只有个位数（3 之类），

用户报障原话：「制作代理有个bug，会莫名奇妙不识别，隔一会又好了」。定位过程与结论：

- **反馈环**：`Player.log` / `Player-prev.log` 全量搜 `DigitalStorage`/数字存储/制作代理 **0 命中**（`DS_EnableDebugLog` 没开），
  也没有本 mod 的异常 —— 说明不是异常路径，是**状态卡住**；那两条会 `Log.ErrorOnce` 的 5 秒退避（`CompBillAutomation.cs:583/:658`）也被排除。
- **根因（代码级确证）**：代理把「自己造的 bill」长期换进台子选料，而原版
  `RimWorld\WorkGiver_DoBill.cs:263-266` 在**每次选料失败**后写
  `bill.nextTickToSearchForIngredients = now + ReCheckFailedBillTicksRange.RandomInRange`（`:95`，**500~600 tick**），
  `:194` 的硬闸又会在 `TicksGame <= bill.nextTickToSearchForIngredients && FloatMenuMakerMap.makingFor != pawn`
  时**整条跳过这张 bill**（我们借台子时 `makingFor` 恒为 null ⇒ 永远命中）。
  关键点：我们这条 bill **不是临时的**（`CompBillAutomation.MakeLine:419-426` 创建后随 `CraftLine` 活到 `ClearAll`），
  所以原版的负缓存**粘在它身上**：任何一次取活失败（刚做完一件还没补料 / 另一条线占着这堆 / 料被顺走几件）之后，
  代理对本线失明 8~10 秒（1×），且退避期间面板照旧报「缺料（核心里的材料不足）」或干脆「等待中」——
  与「不识别、隔一会又好了」完全吻合。顺带修一个同源隐患：同一次取活里会依次问多个 `WorkGiver_DoBill` 派生类，
  前一个失败写的缓存会让**后一个 giver 直接拿到 null**。
- **改动**（`Source/AI/BillProbe.cs`）：新增 `ResetVanillaNegativeCache(Bill)`，在**每次** `doBill.JobOnThing(...)` 之前把
  `bill.nextTickToSearchForIngredients` 归零；`Diagnose` 判定 `DS_BA_Block_Material`（真没料）时退避改 `CraftBackoffTicks`
  （120 tick / 2 秒）而不是 30，因为清掉负缓存等于把「原版全图候选遍历」的天然限频也清掉了（`WorkGiver_DoBill.cs:525-551`，
  `ingredientSearchRadius` 默认 999 ⇒ 整张图），必须自己限频。`BillProbe.cs:33-35` 那句「我们的 bill 是临时的，写它也没意义」的旧注释是**错误前提**，已改写。
- **效果**：材料恢复后 ≤2 秒重新开工（原来最多 8~10 秒），且失败原因不再被负缓存污染（诊断可信）。
- **校验**：Release 0 error（仅 `AssemblyInfo.cs(16,31)` CS0618 旧警告）；csproj↔磁盘 106=106；DLL `Patch_*` 75；
  DLL SHA-256 `9070A7F847CBB9A6D2A029D2050ED2DEA629554DDB0D5151A1F2A52E1B68BE05`；`Tools\deploy.ps1` 已同步游戏目录（哈希一致）。
- **埋点**：`BillProbe` 外面包了一层 `TryAcquire` 壳，只在 `enableDebugLog` 打开时按「原因变化 / 300 tick」节流打印
  「制作代理取活 成功/失败：原因｜配方｜台子｜清掉了原版负缓存（还剩 N tick）」—— 报障时这一段就是第一现场证据。
- **待实机验证**：让核心短暂缺料（做一件消耗光）→ 补料 → 代理应在 ≤2 秒内开工；若仍复现，下一步开 `DS_EnableDebugLog`
  抓「取活失败原因」逐轮序列（见验收清单新增条目）。
