### 制作代理：允许 `UsesUnfinishedThing` 配方（一步成型，跳过未完成品）

玩家实机回填调查行：**`范围内配方 60 个：可添加 3 · 研究未解锁 0 · 不支持 57`**

### 严重 bug：堆叠 mod 把 stackLimit 抬到千万级 ⇒ 核心容量判定 int 溢出（已修复）


来源：用户当天报障（两张截图 + Player.log）：**地面上的白银/零部件死活不进核心**；右键菜单只给
「从数字存储取出…」，原版那条灰着写「未配置空余的、可到达的储存点」；顺带删储存区时刷红字
`Removing haul destination that isn't registered 储存区 1`。

**取证（Dev 动作「为何没被自动收纳（点格子）」的 dump 是决定性证据）**：

```
[3] Building_StorageCore prio=Preferred enabled=True accepts=False spawned=True 阵营=新移民 被禁=False 距离=2.2
核心「数字存储核心」 在目的地表里=True ... HaulDestinationEnabled=True 优先级=Preferred
                    Accepts=False 筛选允许=True 还能装=-1326444032 被禁=False 阵营=新移民
```

表里有核心、通电、开关全开、筛选允许 —— 只有 `Accepts` 是 false，而且 `还能装` 是**负数**。
存档侧也全部复核过（`Faction_16` = 玩家、无 `<forbidden>`、`<priority>Preferred</priority>`、
`allowedDefs` 里 `Silver`/`ComponentIndustrial`/`Steel` 都在、13/3000、`spawnedTick=32277`）。

**反解**：核心 `maxStacks=3000`、`Count=13` ⇒ 剩余堆位 `k=2987`；原版容量 =
`int((3000-13) * stackLimit)`，观测 `-1326444032`，即 `2^32-1326444032 = 2,968,523,264`。
解 `2987 * L ≡ 2,968,523,264 (mod 2^32)` 得 **L = 24,000,000**
（2987 × 24,000,000 = 71,688,000,000 → mod 2^32 = 2,968,523,264 → int32 = -1,326,444,032，与 dump 逐位吻合）。

**24,000,000 从哪来**（玩家整合包两条叠加，全部逐行读源码确认）：

1. Steam `simple.tech`：`1.6\Patches\Increased Stack.xml` 的 `PatchOperationReplace` 把
   `Silver/stackLimit` 改成 **30000**（`ComponentIndustrial` 750、`ResourceBase` 7500、`Gold` 30000…）。
2. Steam `OgreStack`：`OgreStack.CategorySetting.ProcessThing` 先 `GetBaseStackLimit(def)`
   （静态 `_baseCounts` 缓存第一次读到的值，此处即 30000），再按模式改写：
   `Scalar` ⇒ `num = max(1, floor(base * Value)); def.stackLimit = num;`
   玩家配置 `Mod_1447140290_OgreStackMod.xml` 里 `SmallVolumeResource_Mode=Scalar`、
   `SmallVolumeResource_Value=800`，而 `OgreStack.Support.RimWorld` 判
   `SmallVolumeResource = FirstThingCategory == "ResourcesRaw" && d.smallVolume` —— 白银正中该桶
   ⇒ **30000 × 800 = 24,000,000**。零部件走 `Manufactured`（`Manufactured_Value=5000`）⇒ 750 × 5000 =
   **3,750,000**（2987 × 3,750,000 = 11,201,250,000 → int32 = -1,683,652,888，同样为负 ⇒ 同样 `Accepts=false`）。

**为什么别人没撞上**：原版货架类 `Building_Storage.maxStacks` 只有个位数（3 之类），
`3 × 24,000,000 = 72,000,000` 远没到 `int.MaxValue`；本 mod 的 3000 堆 × 八位数 `stackLimit`
才是唯一会撞穿 2^31 的组合。所以这不是"堆叠 mod 有 bug"，是**两边都没错、只有大容量容器 + 超长堆叠的交叉点会炸**。

**根因位置**：`Verse.ThingOwner.GetCountCanAccept`（线上 1.6.9676.17735 程序集反编译与我们本地树逐句一致）：

```csharp
int num = 0;
if (Count < maxStacks) num += (maxStacks - Count) * item.def.stackLimit;   // ← 纯 int 乘法，无溢出保护
```

调链：`Building_StorageCore.Accepts` → `innerContainer.GetCountCanAccept(t) > 0` → 负数 ⇒ false ⇒
原版 `StoreUtility.TryFindBestBetterNonSlotGroupStorageFor` 的 `!Accepts` 门跳过核心 ⇒
本 mod `CompAutoIngest.WouldVanillaHaulIntoCore`（先问原版，再自己收）也跟着把这批货全丢 ⇒
用户看到的就是"白银/零部件站在地上没人搬，而且一点红字都没有"。**两个症状同一个根因。**

**修法**（三处）：

1. `Source/Core/CoreStorageContainer.cs`：新增 `internal int CountCanAcceptSafe(Thing item, bool canMerge = true)`，
   与原版逐句对齐、只把累加器换成 `long`，末尾夹到 `[0, stackCount]`；
   `GetCountCanAccept` 覆写改为调它 ⇒ `Accepts`/`TryAdd`/`CanAcceptAnyOf`/取料侧全部自动受益
   （`TryAdd` → `base.TryAdd` 内部也只问 `CanAcceptAnyOf`，同一条虚方法）。
2. `Source/HarmonyPatches/Patch_HaulDestinationManager_RemoveGuard.cs`（新文件，**已补 csproj 一行**）：

   把原版那句 `Log.Error` 降级成开发者模式 `Log.Message`。原版失败分支本身也只是 error+return、不动任何列表，
   所以**行为等价**，只去掉红字。真·重复登记（我方兼容替身重复 Add）仍然照报。
3. `Source/Components/AutoIngestDevTool.cs`：dump 增加 `stackLimit=`（原版值 vs `long` 版容量），

**校验**：Release **0 error**（唯一警告仍是 `Source/Properties/AssemblyInfo.cs(16,31)` CS0618）；
`csproj ↔ 磁盘` **116 = 116**（新增的补丁文件已登记，`Compare-Object` 无输出）；

  `RimWorld\WorkGiver_DoBill.cs:263-266` 在**每次选料失败**后写

  `bill.nextTickToSearchForIngredients` 归零；`Diagnose` 判定 `DS_BA_Block_Material`（真没料）时退避改 `CraftBackoffTicks`
